# plan_reader.mjs: საკადასტრო გეგმის ამოცნობა "საკადასტრო რუკის" PDF-ებს შორის

კონტექსტი `napr_amonaweri_instruqcia.md`-სთვის (ნაწ. 4, 6, 7). `plan_reader.mjs` ცვლის ინსტრუქციის `pdfText`/`describePdf`-ს. გვერდის წაკითხვა (`parseAbstractPage`, `readList`) და ამონაწერის ლოგიკა (`findExtract`) უცვლელი რჩება.

## 1. მოკლედ

- ინსტრუქციის `describePdf` შემოწმებულ 18 ნამდვილ გეგმიდან **მხოლოდ 4-ს** ცნობდა. 01.10.14.028.016-ზე `findCadastralPlan` დააბრუნებდა "ვერ მოიძებნა", თუმცა გეგმა სიაში არის.
- `plan_reader.mjs`-ის `describeMap` 18-ვეს ცნობს. რეესტრის 3 ნახაზს და აზომველის 11 ფაილს გეგმად არ თვლის.
- **გეგმას ნახაზისგან მხოლოდ სათაური არჩევს: "საკადასტრო გეგმა" / `sakadastro gegma`.** მეტამონაცემები (Producer, Creator, PDF-ის ვერსია), განცხადების ნომერი, "საკადასტრო კოდი" და სააგენტოს სახელი ამისთვის არ გამოდგება: რეესტრის ნახაზებიც იმავე ბლანკზეა.

## 2. ჩასმა

```js
import { describeMap } from "./plan_reader.mjs";
// findCadastralPlan-ში:  info = await describeMap(await fetchBytes(r.url));
```

- `kind`-ის მნიშვნელობები ინსტრუქციისავეა (`cadastral-plan`, `situational-drawing`, `measurement-drawing`, `unknown`), ამიტომ დანარჩენი ლოგიკა არ იცვლება.
- გარე ბიბლიოთეკა არ სჭირდება. იყენებს მხოლოდ `DecompressionStream`-ს, ხოლო MD5 და RC4 კოდშივე წერია. მუშაობს Chrome-ის service worker-შიც და Node 18+-ზეც.
- ფაილი ES module-ია (`export`). MV3 ექსთენშენში: `"background": { "service_worker": "background.js", "type": "module" }`, ან კოდი პირდაპირ ჩასვი background-ში და `export` წაშალე.
- სიჩქარე: ფაილზე 15–100 მწმ, ხელმოწერილ 2016–2021 წლის ფაილებზე 0.5–0.9 წმ (Node-ში გაზომილი).

`describeMap(bytes)` აბრუნებს:

| ველი | რა არის |
|---|---|
| `kind` | `cadastral-plan` / `situational-drawing` / `measurement-drawing` / `unknown` / `encrypted-unsupported` |
| `stamp` | რეესტრის შტამპის ტექსტი, თუ არის (მაგ. `SidaazomviTinaxaziarSeesabameba`). მომხმარებლისთვის საჩვენებლად, `unknown`-ის ასახსნელად |
| `confirmed` | გეგმაა და აქვს სააგენტოს სახელიც (დამატებითი ნიშანი, არ არის გადამწყვეტი) |
| `appNo` | განცხადების ნომერი ტექსტიდან (12 ციფრი, `88…` **ან `89…`**) |
| `prepared` | "მომზადების თარიღი" (მხოლოდ 2016-დან, `dd/mm/yyyy`, დროის გარეშე), სხვაგან `null` |
| `created` | `/CreationDate`, დაშიფრულ ასლებშიც გაშიფრული |
| `signed` | `/ByteRange` არის |
| `encrypted` | ფაილი დაშიფრული იყო (და გაიშიფრა) |

## 4. რატომ ვერ ცნობდა ინსტრუქციის კოდი და რა გაკეთდა

1. **დაშიფრული ასლები (2016–2021).** Standard security handler, V2/R3, RC4 128-ბიტი, ცარიელი მომხმარებლის პაროლით. ფაილი პაროლის გარეშე იხსნება, მაგრამ ნაკადები დაშიფრულია.
   - შედეგი ძველი კოდით: ცარიელი ტექსტი, ან ნაგავი.
   - გაკეთდა: გასაღები (Algorithm 2: MD5, 50 გამეორება) და ობიექტის გასაღები, RC4 გაშიფვრა. `/CreationDate`-იც იშიფრება.
   - AES (V4+) **მხარდაჭერილი არ არის**, ასეთი ფაილი არ შემხვედრია. ასეთ შემთხვევაში ბრუნდება `encrypted-unsupported`.
2. **ლათინური სათაური (AcadNusx) ძველ გეგმებში.** ინსტრუქცია მხოლოდ ქართულ `საკადასტროგეგმა`-ს ეძებდა.
3. **Ghostscript-ის ფონტები:** ბაიტები `\x01, \x02…`, ასოები კი `/Differences [1 /m /i /w /s /space …]`-შია. ნედლ ბაიტებში "sakadastro" არ წერია.
   - გაკეთდა: თითო ფონტისთვის ცალკე დეკოდერი, თანმიმდევრობით: ToUnicode → `/Differences` (glyph-სახელი: ერთასოიანი = ის ასო, + `space`, `period`, `zero`… `nine`, `uniXXXX`) → Latin-1.
   - შენიშვნა: ინსტრუქციის კოდი ყველა ToUnicode ცხრილს ერთ ცხრილად აერთიანებს. ეს არასწორია, თუ ფონტებს სხვადასხვა კოდები აქვთ.
4. **ინლაინ სურათები (`BI … ID <ბინარი> EI`) კონტენტ-ნაკადში.** ბინარში შემთხვევითი `(` ტექსტის ამოღებას ჭრის, ამიტომ ეს ბლოკები ამოიჭრება.
5. **ObjStm (შეკუმშული ობიექტები).** ფონტების ობიექტები იქიდანაც იკითხება.
6. **literal string-ების escape-ები** (`\(`, `\)`, `\ddd` რვაობითი) სწორად იშიფრება.

## 7. ინსტრუქციის ტექსტში გასასწორებელი

- **ნაწ. 4, ცხრილი:**
  - "საკადასტრო გეგმა — ქართულად: `საკადასტრო გეგმა`" → 2016 წლამდე გეგმებში ლათინურადაა `sakadastro gegma`.
  - "აზომვითი ნახაზი — `azomviTi naxazi`" → რეესტრის სიის ფაილებში ეს ფრაზა მხოლოდ შტამპში ("…არ შეესაბამება…") გამოჩნდა და დოკუმენტის ტიპს არ ნიშნავს.
  - "დაშიფრული ასლი — ტექსტი არ იკითხება" → იკითხება (RC4, ცარიელი პაროლი). ეს გეგმებზე დადასტურდა, ამონაწერებზე არ შემოწმებულა.
- **ნაწ. 6, ნაბიჯი 3:** "გეგმის ტექსტში მომზადების დრო არ წერია" → 2016 წლიდან წერია "მომზადების თარიღი: dd/mm/yyyy" (დროის გარეშე). ძველ გეგმებში თარიღი `dd.mm.yy` ფორმატშია, ცალკე, და `prepared`-ში არ შედის. ერთი განცხადების რამდენიმე გეგმის დასალაგებლად `/CreationDate` კვლავ საუკეთესოა (ახლა დაშიფრულ ასლშიც).
- **ნაწ. 6/7, ტიპების რიგი:** ჯერ შტამპების ამოჭრა, შემდეგ ნახაზის სათაურები, ბოლოს გეგმა (ნაწ. 5).
- **განცხადების ნომერი** შეიძლება `89…`-ით იწყებოდეს (`892012158903`, `892024931241`). სივრცეების მოშორების შემდეგ რიცხვის ძებნა ცრუ ნომრებს იძლევა (კოორდინატები ერთმანეთს ეწებება). `plan_reader` ეძებს: `*N*` (შტრიხკოდი), "განცხადების ნომერი: N", ან ძველ ფორმატში თარიღის (`dd.mm.yy`) შემდეგ.

## 8. რაც არ შემოწმებულა

- სხვა ტიპის დოკუმენტები "საკადასტრო რუკის" სახელით (ტოპოგრაფიული გეგმა, გაყოფის ნახაზი და სხვ.). ასეთი ჩვენს ნიმუშებში არ იყო. თუ სათაური ტექსტადაა და "საკადასტრო გეგმა" არ წერია, დაბრუნდება `unknown`.
- AES-ით დაშიფრული ფაილები.
- დაშიფრული **ამონაწერები**. სავარაუდოდ იგივე სქემაა და იკითხება, მაგრამ ტესტი არ ჩატარებულა.
- ფაილები, სადაც სათაური მრუდებადაა დახატული (Chromium-ის გეგმებში ასე მხოლოდ ბადის ციფრებია, სათაური ტექსტია).
- `parseAbstractPage`/`readList` ცოცხალ გვერდზე ამ ჩატში არ გაშვებულა. შემოწმდა მხოლოდ PDF-ების ამოცნობა, ჩამოტვირთულ ფაილებზე.
